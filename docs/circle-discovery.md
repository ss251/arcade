# Circle-shaped discovery

ARCADE exposes `/.well-known/x402` with registry-shaped `items` and the existing
`resources` alias. Each item includes `type: "http"`, `x402Version: 2`, a public
resource URL, the exact unsigned root `accepts` and provider/request metadata.
The options are generated by the same built/listed rail selector as the paid
endpoint; discovery does not verify a payment or ask a provider for support.

`/openapi.json` carries the same metadata in each paid operation's
`x-circle-metadata`, and the items in `x-circle-discovery`. These are OpenAPI
extensions, not invalid unprefixed operation fields. The public schemas, price,
seller address and observed seller ENS name are exposed; no private manifest,
key name, engine configuration or stored-record extras are spread into metadata.

Provider `website` and `docsUrl` point to the listing page. An ENS seller name is
used only when an existing stored skill-name observation matches the configured
current listing and has not been observed unavailable. Otherwise the address is
used. Rendering performs no new ENS lookup and does not establish fresh ownership
or continuous liveness.

## Current wire shape and compatibility

Circle's current [discovery reference](https://developers.circle.com/agent-stack/agent-marketplace/discovery-api)
and the captured CLI item use `metadata.input`, `metadata.output` and `siwx`.
ARCADE emits an HTTP/POST/json input descriptor with the declared body schema,
the declared output schema, and `siwx: false`. The plan's `inputSchema` and
`outputSchema` names remain explicit aliases, not a claim that the upstream
registry used those names. Current documented categories include
SOCIAL_INTELLIGENCE; the earlier approved DATA_ENRICHMENT value remains accepted
locally without an automatic migration.

Support flags describe this listing's selectable choices, not the entire hub's
construction inventory. A Gateway-only listing/hub has vanilla support false;
an exact-only listing has Gateway support false; an unavailable escrow-only
listing has both false and no accepts. Test mode keeps its simulated challenge
but advertises neither production capability. A renderer called without prepared
challenges likewise emits no accepts rather than inventing payment terms.

The bounded Graph splitter generator reads the `resources` compatibility view.
It selects only a vanilla exact accept, wherever it appears, and still requires
the immutable reviewed splitter/seller pin. Gateway/escrow destinations and
unavailable listings are never promoted into splitter inventory. The generator
retains its EIP-3009-default gate; registry provider metadata cannot authorize a
new splitter. Legacy single-accept documents remain readable.

The [scrubbed historical CLI sample](evidence/J/registry-item-sample.json) records
the free search command, output hash, time and redactions. It is a metadata
fixture; its merchant endpoint was never invoked. One earlier capture attempt
successfully ran the CLI but failed to unwrap its JSON `data` envelope; the
retained capture corrected that parser. Existing terms acceptance was unchanged.

## Claim boundary

This checkpoint proves local registry-shaped metadata and offline agreement
between discovery and HTTP402. It does **not** prove Circle CLI inspect/pay
compatibility, a paid wallet call, live Gateway availability or an escrow rail.
Those require the later named live proofs. It does not list ARCADE in Circle's
marketplace or submit its intake form.
