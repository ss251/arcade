## 2. Lineage wire design (resolved)

- **Issuance.** When the hub creates a job (`store.putJob`), it also computes `hireCapability = HMAC-SHA256(ARCADE_HUB_SECRET, "arcade-hire:" + jobId)` and sends it in `JobAssignment.hireCapability` together with `JobAssignment.parentJobId` (undefined for root jobs). Domain-separated from the buyer's result token (`"arcade-job:"`), so a result token never authorises spending and vice-versa.
- **Runner.** `daemon.ts` passes `hireCapability` into `broker.openJob(jobId, budgetUsd, hireCapability)`. The broker's purchase adds header `x-arcade-lineage: base64(JSON {parentJobId: jobId, hireCapability})` to both the probe and the paid retry via `PurchaseArgs.lineage`. Nothing else is client-supplied.
- **Hub check at `POST /x/:seller/:skill`** (before `rail.verify`): if the header is present, verify the HMAC against `parentJobId`, load the parent via `store.getJob`, require parent status `running`, derive `rootJobId = parent.rootJobId ?? parent.id`, `hop = parent.hop + 1`, `ancestors = parent.ancestors ∪ {parent.skillId}`. Refuse: `lineage_invalid` (bad MAC or unknown/finished parent), `lineage_cycle` (`listing.id ∈ ancestors`), `lineage_depth` (`hop > 2`), `tree_budget_exceeded` (reservation fails). No header = root buy, hop 0 — honest, because a raw x402 client is a new customer.
- **Reservation ledger.** `tree_reservations` keyed by `rootJobId`: `ceilingAtomic` from the root listing's `bounds.maxSubSpendUsd` (0 if absent), `reservedAtomic`, `committedAtomic`. Reserve `priceAtomic` inside one SQLite transaction at child 402 acceptance (`reserved + committed + price ≤ ceiling` else refuse); on child receipt: settled → move reserved→committed; not settled → release. Root job terminal → release any residue.
- **Job and receipt fields.** `Job` gains `parentJobId?`, `rootJobId`, `hop`, `ancestors[]`. `Receipt` gains the same plus `children: [{jobId, skillId, priceAtomic, settled, settleTx?}]` and `receiptSignature` (EIP-191 by the facilitator over the canonical JSON of the tree). `/jobs/:id/result` returns the tree to the token holder; `/receipts` keeps omitting `jobId` and `buyer`.
- **Claim.** "Hub-attested receipt tree with chain-auditable edges." A stranger verifies each disclosed settle tx (`from` = hiring seller's sub-buy wallet, `to` = hired seller or FeeSplitter, `value` = listed price, and the `Settled` nonce for splitter payees) and the hub's signature. Completeness is attested, not proven. Nonce-commitment into EIP-3009: **not built**; would break third-party x402 clients.

## 3. ERC-8004 plan

- `IdentityRegistry(0x8004A818BFB912233c491871b3d84c89A494BD9e).register(agentURI)` from the **seller key** (owner = seller) for the featured skill on first `arcade start`; `agentURI` = the hub's public listing URL. Emits `Registered`. Persist `agentId` in `~/.arcade/config.json` (public data).
- `ReputationRegistry(0x8004B663056A597Dffe9eCcC1965A193B7388713).giveFeedback(agentId, 1, 0, "arcade-settled", skillId, "<hub>/x/<seller>/<skill>", "<hub>/receipts/<jobId>.json", keccak256(receiptJSON))` from the **hub attester key** (funded with faucet USDC for gas, distinct from the facilitator and never the seller), only after `receipt.settled === true`, best-effort, retried once, never blocking or reverting settlement. Receipt JSON carries `proofOfPayment: {fromAddress, toAddress, chainId: 5042002, txHash: settleTx}` per the ERC's feedback file schema.
- Display: "settled feedback from ARCADE attester: N" on the listing page and in `arcade_describe_skill`, filtered by `clientAddress == attester`. **Not claimed to be** reputation, a score, or Sybil-resistant; claimed to be *settlement evidence on the chain the settlement happened on*. Never read `getSummary`; never gate a payment on it.
- ENSIP-25 pointer on the seller's ENS subname closes the loop (section 5).
