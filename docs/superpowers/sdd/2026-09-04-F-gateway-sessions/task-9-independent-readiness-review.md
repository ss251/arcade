## 1. MCP cancellation is currently discarded before its purchase queue

Observed source:

- `packages/buyer/src/mcp.ts:801–803` ignores the request handler's second argument. Installed `@modelcontextprotocol/sdk` **1.29.0** supplies `extra.signal` (`dist/esm/shared/protocol.d.ts:173–177`); its implementation aborts on cancellation at `protocol.js:174–175` and connection close at `259–260`, then suppresses an aborted request's outgoing response at `371–375`. It does not stop application work that ignores the signal.
- `mcp.ts:91–96` waits for a plain Promise predecessor, then executes work unconditionally. `handleTool:530–534` passes no signal; the paying `Effect.runPromise` at `666–670` receives none. Consequently, a queued call can execute after its requester canceled/disconnected, while the SDK discards the eventual response. This is a source-composition finding, not a test run here.
- Installed Effect already supports `Effect.runPromise(effect, { signal })` (`Effect.d.ts:24422–24423`); no dependency upgrade or global cancellation mechanism is needed.

Narrow F10 recommendation, parent accepted: pass the SDK signal through the session/lifecycle dispatch and queue entry, check it before joining and again immediately after acquiring the lease, and pass it to the Effect runtime. An aborted queued operation must not later discover/sign/open/close. Aborting a middle waiter must **not release its successor ahead of the still-running predecessor**. Retain conservative issued exposure when abort occurs after signer entry; release only a definitely unsigned reservation. Fixed local errors must not reflect `signal.reason` or raw cancellation diagnostics. Preserve ordinary behavior outside the narrowly integrated cancellation boundary.

Future genuine tests: hold operation A; enqueue B then cancel it; enqueue C; assert B never begins and C remains blocked until A finishes. Repeat with cancellation notification and transport disconnect through actual in-memory MCP transport, not only direct `handleTool`. Abort an active session probe and an active signer separately: probe case has zero signatures; signer case retains exposure, with zero late paid POST after abort. Ensure every queue lease eventually releases after bounded operation cleanup, without resetting counters.

## 2. Direct BuyerSession needs its own issued-exposure ceiling

The accepted notes explicitly conserve MCP process exposure, but the SDK API can be used without MCP. Current local counters live only in `mcp.ts:85–103,659–680`; `fetchWithPayment` has only a per-call amount cap. F5's hub ledger cannot account for an authorization it has not received. The signed message also contains neither session ID nor job ID (`gateway-sign.ts:103–105`; `eip3009.ts:516–526`), so local cancellation or a session release is not revocation.

Concrete source-composition scenario: captured session budget 10, first explicit call signs 6 and its paid POST is lost before admission; authenticated hub status still reports remaining 10. A second explicit call that uses only hub remaining can sign another 6. Serializing calls and latching each Effect once do not prevent this; the operations are distinct and sequential. The hub may ultimately reject one admission, but 12 of authorization authority has already been issued. This is not a demonstrated remote settlement or an assertion that the honest hub admits over budget.

Narrow F9 recommendation, parent accepted: maintain private per-BuyerSession operation/exposure records, in addition to F10's process ceiling. Reserve the bounded amount before signer invocation, count signer-entered but unresolved amounts conservatively, and cap a new signature by both captured budget/exposure and validated hub remaining. Correlate operation, accepted job, amount and validated terminal reference exactly once. Combine local and hub evidence without counting the same admitted obligation twice, but do not discard an uncorrelated issued amount merely because it is absent/released in hub status. Unknown overlap may conservatively refuse; it must not enlarge capacity. Settled observations move an obligation from unresolved to spent once, rather than adding it again at status/close. No exported reset, token access, automatic retry, global SDK session or persistence expansion is needed.

Future genuine tests: use budget 10 and two calls of 6 after a lost first paid POST, both sequentially and concurrently; only the first may sign. Repeat after hub status says released or returns a valid closed artifact: exposure remains, even though hub held is zero. Test a known matching held/settled call avoids double counting, foreign/mismatched jobs do not clear exposure, and repeated status/close reconciliation changes counters at most once. Across separate SDK sessions, F10 must still retain its original cumulative process exposure; SDK-local accounting is not a process-wide or wallet-wide spending guarantee.

## Concrete implementation checks under already accepted decisions

1. **Effect ownership must live outside evaluation.** `fetch-with-payment.ts:144–159` captures options inside `Effect.gen`, and both signers prepare a fresh nonce on evaluation. Reusing that Effect is not one-shot; the existing payment-header guard only protects an already-paid RequestInit. F9 should allocate a private shared attempt state when each operation is created, then synchronously claim it on first execution before any mutation/signing. Concurrent evaluation of that same Effect, retry after failure, and re-evaluation after interruption must not reset it. Separate explicit call invocations remain separate operations, still subject to the session ceiling. Allocation alone must do no network/signing. Snapshot supported input/body and authority before the first await; later caller mutation cannot change a queued purchase.
2. **Effect interruption is not fetch/signer cancellation by itself.** The current probe and paid fetch (`fetch-with-payment.ts:179–190,270–274`) ignore the Effect-provided signal; only replay-body acquisition uses it. Gateway signer invocation (`gateway-sign.ts:116`) and the ordinary signer (`eip3009.ts:509`) also accept no abort signal. F9 needs operation-local active/deadline guards immediately before invoking the captured signer and before forwarding paid bytes, plus bounded abort-aware captured transport. Mark potential issuance at signer entry, not merely when its Promise resolves: a signer can issue then stall/throw. A late signer result must not restart the canceled operation. Fixed-error mapping cannot turn interruption into success or drop conservative exposure. Preserve F2 canonical frozen requests/recovery; no broad legacy rewrite is required.
3. **Use the new token-free session polling contract, not the stale paragraph.** The original readiness's instruction to extract a query token is superseded by the parent's final crossnote. Current `index.ts:122–138` ignores `job_token` and allows legacy query tokens. F9 must decode the explicit opaque job capability and send `x-arcade-session`, `x-session-token`, `x-job-token` only to the exact query-free owned-origin job-result path. All present/empty/conflicting session state is fail-closed, never ordinary fallback. Do not call legacy `/jobs/:id` or receipt-tree as recovery. Actual F8 frozen response shapes remain the final decoder dependency.
4. **Polling needs an elapsed deadline and accurate phase states.** Current `index.ts:131–158` counts attempts, not elapsed body time; the current ordinary server long-polls up to 120 seconds (`server.ts:1250–1295`). A short per-read timeout may abort a legitimate pending job, while an attempt count alone may run far beyond advertised maxWait. Give F9 a finite overall deadline, bound each pending read to its remainder and account for the actual F8 long-poll contract. Only the exact valid 202 pending shape may poll again; `session_settlement_uncertain` must not be retried as pending. Timeout after signing retains exposure and returns a fixed unknown/pending result, never “not charged.” Test a delayed valid terminal body, stalled body, late fetch resolution, deadline exhaustion and cancellation; no new signing or paid resend in any case.
5. **Require local signing provenance before paid success.** Existing `fetchWithPayment:184–185` accepts a non-402 as `paid:false`. F9 must not trust a forged 202/terminal session response or provider-supplied authorized amount as proof of a locally paid operation. Require the accepted paid path, exact locally known amount, job/target/session/rail correlation and strict F8 terminal receipt before releasing output/accounting it. A second 402 must not sign again. For test rail, USDC-shaped metadata is not evidence of simulated-only authority: actual `test-rail.ts:45–57` publishes the ordinary domain. Do not treat invoking a real signer as exposure-free merely because the hub labels its rail `test`.
6. **Read-only MCP tools must stay bound to captured identity.** Current `arcade_budget` re-reads `buyerAccount()` at `mcp.ts:740–744`. An active/uncertain session's status/close/budget must use its captured public buyer/chain/origin, not silently display or select a subsequently changed environment wallet. Read-only recovery needs no fresh signing-key retrieval. Keep bounded balance failure separate from session status, report unavailable data honestly, and never label Gateway credit as wallet USDC. This follows the accepted capture rule; it does not authorize a new balance/funding client.
