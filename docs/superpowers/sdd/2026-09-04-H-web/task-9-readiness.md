## Concrete literal-plan mismatches

1. **Browser-only custody conflicts with both current and proposed relays.** T-PRIV-003 says the web service cannot re-fetch a buyer result. Current `api.settle.ts:66–103` receives the ordinary 202 `poll_url?token=…`, holds that capability while polling through `hubJson`, and returns only the terminal body. The hub terminal body does not echo `job_token`. Task 10's remember-after-done therefore normally stores nothing. Proposed GET server function `treeFor({jobId,token})` would additionally transmit the browser capability to the web application/SSR server, irrespective of whether it persists it; a GET server-function transport may also put serialized input in its request URL. Do not implement that server-function API or call the relay browser-only custody.
2. **Capture acceptance, not just success.** The ordinary 202 carries `job_id`, `job_token`, `poll_url`, `price`; capability recovery matters especially when result polling later fails. Capture a validated, same-origin-bound acceptance before polling, persist separately from transcript/model data, and mark pending/unknown honestly. A lost paid response before the browser receives a capability remains unrecoverable by this store; never invent one or resend payment.
3. **The plan's storage decoder is not a decoder.** `Array.isArray(parsed) ? parsed as StoredJob[] : []` admits null rows, malformed money/tokens/timestamps, duplicates and unbounded arrays/strings. Its example tokens `tok_a`, job IDs `job_old`, `b`, session `sess_1` contradict actual canonical contracts. Replace fixtures with real-shaped synthetic values; missing-module failure is setup, not a behavioral Red. `history.ts` has a similar unchecked read, so it is not a safe capability-store template.
4. **Capabilities need a realm, not only a job ID.** Store-bound issuing hub origin is required: `arcade-job:<jobId>`, `arcade-session:<sessionId>` and `arcade-session-job:<sessionId>:<jobId>` are distinct HMAC domains despite all tokens being 32 lower-case hex. Same IDs on another hub must never receive the old capability. `sessionId?` alone cannot authorize status or result retrieval. Never infer realm from a token's shape or from a server response that was not correlated to its accepted context.
5. **F's actual API differs from the plan.** Session IDs are `ses_[a-f0-9]{32}`; status includes `network`, `held`, `complete`, per-call `state`, and optional authoritative `closed_receipt`. Reference kinds are `onchain`, `gateway-transfer`, `test`, not `gateway-batch`. F's paid 202 does **not** echo `session_id`; it is known in the selected session closure. `openSessionPromise` returns identity plus `quote/call/status/close`, hides the session token, and `call` returns a `SkillResult` without job token. There is no capability export/import/resume API. `status()` can recover a lost close on the existing handle; process/page exit cannot reconstruct that handle. Do not intercept injected fetch merely to siphon its private tokens into storage or spread its internal objects into UI/history.
6. **Session jobs are not ordinary tree capabilities.** F polling requires all three headers (`x-arcade-session`, `x-session-token`, `x-job-token`) at the captured origin. Missing/present-empty/foreign headers must not fall back. `/trees/:root` currently accepts only the ordinary root token; a session token is correctly refused there. F session artifacts account admitted roots and intentionally omit child-tree evidence; never label a session group as a complete graph or offer ordinary tree retrieval for it.
7. **Gateway signing is not the current chat signer.** `sign.ts:63–128` constructs only the USDC EIP-712 domain and comments that one authorization works on both rails. Actual F uses strict `GatewayWalletBatched`/pinned Gateway Wallet authority, finite validity and recovered signatures. Current `api.settle` also validates settled references as 32-byte hashes, not Gateway transfer UUIDs. H9–10 must not implicitly enable Gateway/session purchases with this signer or advertise that path as working. Correcting the purchase lane needs separately approved scope; preserving E13 approvals/ENS/input/payee/cap binding is mandatory.
8. **Local prices are not proven spend or wallet budget.** Task 10 sums every stored price and labels every `sessionId` group “Gateway sessions.” An accepted or signed call can be reserved, uncertain, released or settled; a session may use EIP/test/Gateway. No `StoredJob` receipt state or budget authority currently exists. Show “locally recorded authorized/accepted amount” separately from validated confirmed settlement; unavailable budget stays unavailable, never zero. Session figures use the actual correlated `budget/spent/held/remaining`, with local issued-unconfirmed exposure retained conservatively; quote is advisory and no debit. Closed/complete is a ledger-state statement, not mining, a refund, withdrawal or global finality.
9. **History/remount cannot safely be an execution trigger.** `Settlement` starts signing in an effect, protected only by an instance ref. Its local outcome is not written back into the AI transcript; history persists the `awaitingSignature` tool output, and selecting a conversation remounts Chat. Source composition therefore allows a restored request to enter a fresh signing effect; actual re-signing is untested here. H10 persistence must distinguish historical display from a newly approved, unused attempt and must not reuse a saved signing request as fresh authority. No token, poll URL or session capability belongs in `UIMessage.parts`: `useChat` sends messages to `/api/chat`, which forwards them to model processing.
10. **Display and async gaps.** Current `Purchase` makes an Arcscan URL for any `settleTx`, and one legacy branch still says “you were not charged.” Carry authoritative rail/network/kind/link eligibility into display; unknown/present-invalid kinds never become legacy-onchain by absence. Preserve `SettlementFailure`'s current uncertainty wording. Task 10 retains the old view during selection changes/failure, has no loading/error state, and does not clear it when selection becomes empty. Clear first, key responses by current selection/realm and ignore late owners. H4 `jsonFetch` has its own bounded read/abort but overwrites an input signal; an effect cleanup flag does not cancel underlying HTTP. Do not claim transport cancellation without an explicit approved signal extension.

## Minimal proposed correction and ownership boundary

- **H9 author:** only `lib/job-store.ts` and `test/job-store.test.ts`. Preserve `KEY = "arcade.jobs.v1"`, base field names and `remember/list/get/forget/forgetAll` where safe. Add required issuing-origin and explicit ordinary realm in an entry or envelope; choose this before code. Keep sessions unavailable rather than pretend `sessionId` is a capability. Make lookup/forget scoped to the captured origin/realm, not a collision-prone global job ID. Reject legacy rows without a provable issuer; do not silently bind them to the current deployment.
- **Closed bounded storage contract:** validate raw byte/character size before JSON parse; explicit row count, exact allowed own data fields, canonical job/token/skill/money grammar and uint256 bound before BigInt, finite nonnegative safe timestamps. Bound origin/string lengths; no getters/coercions on `remember`, no nested capability/payload passthrough. Return independent copies, deterministic ordering and conflict-safe dedupe; a conflicting token for the same realm/job must not silently replace the known one. Proposed local policy (not existing authority): 200 rows and 256 KiB envelope, with visible storage-unavailable/eviction limitation if selected by parent. Do not claim atomic cross-tab exclusion or XSS resistance from localStorage; any same-origin script can read it.
- **H10 UI author:** `routes/buyer.tsx`, scoped styles, route generation and tests; pure `BuyerLedger({jobs,spentAtomic})` can remain only if `jobs` are token-free projections and `spentAtomic` means validated locally known settled amount. `spendOf` may remain a formatting helper over already validated settled rows, not authority derivation. Show local-only history, pending, unavailable, partial tree flags and accurate rail labels. Do not print raw tokens in HTML/attributes/URLs/errors or serialize them in SSR props. Session IDs need not be displayed when a local ordinal suffices.
- **Required parent-approved transport follow-up before browser retrieval claims:** a browser-only bounded `treeFor({jobId,token})` replacement (ordinary realm only), using H4's `TreeView` decoder/presentation contract but **not** server-only `hub.tree` or any `createServerFn` capability input. Server may expose a validated public hub origin without receiving capabilities. Exact origin captured once; fixed route; token header only; `credentials: omit`, `redirect: error`, `cache: no-store`, `referrerPolicy: no-referrer`; whole-body/time bounds, fixed errors and selection ownership. Keep generic public H4 client unchanged unless parent explicitly releases a narrow extraction/signal seam.
- Browser-direct cross-origin header requests need real preflight support. No CORS/OPTIONS handler was found in the examined hub server/session routes; actual deployment proxy behavior was not inspected. Parent must approve a narrow explicit web-origin/method/header CORS allowlist and native browser regression, or leave direct retrieval unavailable. A proxy through the web service is not an equivalent custody boundary. Local `localhost` default also differs from F's literal-loopback origin policy; canonical trusted public origin must be explicitly selected.
- **Purchase boundary is outside literal H10's listed files:** to meet the actual privacy decision, the browser must receive acceptance directly from the issuing hub (including paid submission/response), with current server-side quote/approval checks preserved appropriately. Merely teaching `/api/settle` to return its held token fixes recovery but not browser-only custody. Changes to `api.settle.ts`, `sign.ts`, purchase/quote flow, hub CORS and their tests require separate parent ownership/release; do not quietly expand H9. No new spend/session creation/deposit/close-on-error is authorized by this readiness note.
- For future F session UI, prefer an existing in-browser handle's read-only `status()` while it exists. A restart-persistent capability adapter/export contract needs explicit F approval and dedicated validation, not a new public endpoint or raw credential input box. Until then label session history/recovery unsupported instead of offering fake budget/session/tree panels. Never start/open/reopen a session just to read the dashboard.
