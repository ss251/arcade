# H10 browser-session completeness preflight

2026-09-06. Read-only readiness, not source acceptance or permission to export F capabilities. H9 source/test remain frozen. Only this private report was written; no tests, browser, network, signer, session creation/close/funding, Git or gate ran. The ts-testing skill informed the proposed behavioral matrix, not new tooling or executed Reds.

## Recommendation and completeness boundary

The smallest safe addition is a **status-only view of a legitimately existing, same-document F handle**. It can show the real session ledger budget and recover an acknowledged closed receipt after a lost close response. It cannot restore a handle after reload, native navigation or process exit. Current web source has no `openSession`/`BuyerSession` producer; an empty panel or injected fixture is therefore not proof that real browser session history works.

If H10 acceptance requires durable session history, approve a separate, explicit F **status-recovery export/import adapter** and a separate browser session-realm store. That is a real capability-contract expansion, not a H9 field addition. Do not silently implement it under this readiness release. Neither option requires a create, buy, close, deposit, withdrawal or reopen control: literal Task 10 requests a dashboard, not these mutations. Never create a session merely to populate it.

## Actual contracts versus the literal plan

- Plan H Task 10, lines 3010–3322, assumes optional `StoredJob.sessionId`, a paid response echoing `session_id`, arbitrary grouping labeled “Gateway sessions,” and summing local prices as spend. H9 deliberately has seven ordinary-only fields. Actual F paid acceptance has no `session_id`; selected identity is private context. `SkillResult` does not export a job token. None of those assumed producers exists.
- `packages/buyer/src/session.ts:19–37,128–181,322–343`: both Effect and Promise handles expose identity plus `quote/call/status/close`, not origin or token. Origin, signer/config, session token and issued-call correlation stay private. There is no export/import/resume API. The Promise wrapper is another frozen object, not a serializable session.
- `status()` freshly reads the captured hub through the bounded `sessionRequest`, then validates identity/accounting and reconciles current local state. The current closed-state/fingerprint guards prevent a later contradictory open/changed closed artifact from replacing accepted terminal evidence. Invoke a new status operation for each refresh; never rerun a consumed Effect.
- `session-wire.ts:86–131`: status has actual rail/network, budget/spent/held/remaining, call states, complete/closed and an authoritative closed receipt only when closed. Calls are bounded and correlated; sums/reference categories are validated. **Open status omits buyer**: the current decoder supplies buyer from the original captured identity, whereas the closed receipt explicitly verifies buyer. A restored descriptor's buyer is not freshly corroborated by an open status response.
- `server-sessions.ts:15–21,110–165`: the same `arcade-session:<id>` token authenticates GET status and POST close before Store access. A client object exposing only GET is useful least-surface design, but its exported raw token still grants close authority. Do not describe it as a cryptographically read-only capability. No enumeration/query-token recovery exists; session JSON is private/no-store.
- `server-session-calls.ts:16–55` and `server.ts:1356–1374`: ordinary job, session and session-job HMAC domains differ. Result polling needs the matching session ID/token plus job token. Ordinary `/trees/:id` needs the ordinary root token; session credentials are not interchangeable and must never trigger fallback. F session artifacts account admitted roots and omit child-tree proof.
- T-PRIV-003 excludes capability custody by the web service. Do not implement the plan's `createServerFn treeFor({jobId,token})`, relay a restored session token through `hub.ts`, or put it in SSR/route-loader props, chat/model history, URLs, logs or public receipt projections.

## A. Existing-handle status view: smallest non-export addition

Proposed ownership, only if released: new `apps/web/src/lib/buyer-sessions.ts` (client-only controller) and `apps/web/src/components/buyer-sessions.tsx` (pure token-free view), with `apps/web/test/buyer-sessions.test.ts` and `apps/web/test/buyer-sessions.test.tsx`; integrate the approved `apps/web/src/routes/buyer.tsx`, scoped `styles.css` and generated route tree under the route owner's scope.

- Accept a trusted producer's explicit origin plus only the handle's immutable identity and captured `status` function; use a type-only F import in presentation code. Do not inspect fetch traffic or serialize the handle to discover credentials. Capture/validate the original issuing origin; the facade itself does not expose it.
- Refresh manually with a new `status({signal})`, one current owner at a time. Abort on selection replacement/unmount, ignore late completions, clear stale evidence when authority changes, and render fixed local errors. Preserve the existing whole-body/deadline bound; do not add a second transport or automatic mutation retry.
- Show hub-observed budget, settled spend, held amount and remaining ledger budget separately from the handle's locally issued/confirmed/unconfirmed exposure. Do not sum accepted prices as spend or subtract the two overlapping ledgers again without correlation. These are not wallet balance, Gateway withdrawable credit, a quote to spend, or a process-wide/all-device spending ceiling.
- Distinguish reserved/settling/uncertain/released/settled, unavailable versus genuine zero, and actual `gateway`/`eip3009`/`test`. Gateway transfer UUIDs and test references are not mined transactions. Closed/complete means this session's admitted roots, not graph-wide finality, refund or withdrawal. Use authoritative rail/network/kind before any transaction link.
- Recover a lost close only with GET on that same retained handle and its verified `closedReceipt`; do not invoke `close()` again. An uncertain read must neither invent a closed artifact nor reopen/sign/fund anything.
- **Limit requiring an explicit product choice:** `components/nav.tsx` uses native anchors. Navigating `/chat` → `/buyer` reloads the document and loses a module-memory registry, not just browser refresh. Keeping a handle alive requires a real producer and same-document placement/navigation integration, separately released; CLI/MCP handles cannot be imported by wishful UI state. Without that integration, label the session section unavailable/limited and do not mark durable sessions complete.

## B. Durable status recovery: smallest deliberate new authority contract

Suggested future split, not approved implementation:

1. **F-owned export and reader:** modify `packages/buyer/src/session.ts` only for an explicit opt-in recovery export on genuinely issued Effect/Promise handles; add `packages/buyer/src/session-recovery.ts` for the bounded closed descriptor and signer-free GET-only reader. Use the existing wildcard subpath export; no broad root-barrel/import change is necessary unless the public API deliberately requires one. Reuse `sessionRequest`, `decodeSessionStatus` and closed-receipt validation rather than inventing HTTP/schema rules. Keep the existing spending facade unchanged unless separately authorized.
2. **Descriptor:** version, `realm: "session"`, exact captured `hubOrigin`, canonical session ID/token, buyer, rail/network and decimal budget. Export only from the private legitimate context, not arbitrary object introspection. No signer/account object, payment signature, nonce, paid input/output, job token or issued-call state is implied by this descriptor. Validate closed own data, every scalar/bound and exact origin before storage or request. Do not permit callback/getter/toJSON execution or capability-bearing failures.
3. **Resumed surface:** return a distinct `SessionStatusReader`, never a `BuyerSession`: status only, no open/quote/call/close or signer. Capture origin/fetch once, preserve fixed errors/current-response ownership and immutable terminal-artifact checks. Local issued/exposure counters are **unavailable**, not reset to zero. A metadata-only export cannot safely resume signing because issued-but-unconfirmed authorizations may not exist in hub snapshots.
4. **Authority caveats:** the token can still close the session if used outside this reader; persistence increases its exposure to same-origin scripts. A truly attenuated read-only token would require a new server capability domain/protocol and dedicated tests, not a frontend claim. Open-status buyer cannot be freshly verified from current wire data; retain it only as export-captured metadata, or separately approve a narrow additive buyer field in `server-sessions.ts`/`session-wire.ts` plus compatibility tests before claiming fresh buyer binding. Shape-valid imported metadata is not automatically trusted provenance.
5. **Browser-owned persistence:** new `apps/web/src/lib/session-store.ts` and `apps/web/test/session-store.test.ts`, with a distinct explicit key such as `arcade.sessions.v1`, session realm and origin+session scoped lookup/removal. Keep `job-store.ts` unchanged. Use bounded closed-envelope validation, conflict-safe/no-eviction records, visible unavailable/capacity/recovery outcomes and defensive copies. Never discover another process's private files or dump tokens into an import/export UI without a separate deliberate transfer design. No XSS resistance, cross-tab atomicity or cross-device recovery claim.
6. **Direct transport deployment:** authenticated browser GETs must go directly to the captured hub, header-only, never through Start/server functions. No CORS/OPTIONS handling was found in the examined hub routes; deployed proxy behavior was not inspected. A distinct web origin therefore needs an explicitly approved hub-origin/method/header preflight policy and actual browser fixture proof. A web-server proxy is not an equivalent privacy fix. Retain HTTPS/literal-loopback origin policy; do not alias `localhost`. Current core chain selection is browser-guarded, so the earlier hypothetical `process` crash is not a demonstrated blocker; real browser bundling/framing still needs verification.

This restores status/call summaries and an already-closed receipt only. It does **not** recover paid output: F currently hides session-job tokens and validates terminal results using original authorization/challenge/listing context. Adding result recovery or session trees is another capability/evidence design, not part of the minimum status adapter.
